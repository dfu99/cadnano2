# Lessons — cadnano2

_Hard-won lessons, gotchas, and things that broke before._
_This file is append-mostly. Only remove entries proven wrong._

## General

- Headless testing of AgentMethods works with `QT_QPA_PLATFORM=offscreen` + `cadnano.initAppWithGui()` + a MockDC class. `HeadlessCadnano` is missing `documentWasCreatedSignal`, so the GUI init path (with offscreen platform) is required.
- Insertions in cadnano are position-based, not strand-based. Adding an insertion to a scaffold strand at index X also appears on the staple at index X. `listInsertions` will report both scaffold and staple entries for the same position — this is correct. When adding insertion patterns, only add to one strand type per position.
- `removeCrossoversForPair` removes more crossovers than `addCrossoversForPair` creates — because `addCrossoversForPair` creates double crossovers (2 half-crossovers as one logical unit), but the removal counts each half-crossover individually. This is cosmetic (removal is correct) but the count mismatch can be confusing.
- The DocumentController method for creating a honeycomb part is `actionAddHoneycombPartSlot()`, not `actionNewHoneycombPartSlot()`.
- The autobreak plugin's `__init__.py` has legacy `import cadnano` (not `cadnano2`). To import `autobreak.py` functions from agent code, use `importlib.util` to load the file directly and bypass the package init.
- `Oligo.color()` not `Oligo.getColor()` — cadnano2 uses `color()` as property-style method.
- 1×N linear chain scaffold routing only works for even N ≥ 4. Odd N is geometrically impossible: the honeycomb crossover table ordering (High = Low + 1 for all directions) makes the interior helix constraint (pair_ret < pair_out) incompatible with the end helix parity constraint (even end helix needs pair_out < pair_ret) for adjacent same-direction helices. The 2×N grid avoids this because cross-row connections use different directions with different crossover tables.
- `moveCrossover` had a bug: the overlap check rejected moves even when the only "neighboring" strands were the other half-crossover strands being moved simultaneously. Fixed by collecting `moving_strands` set and skipping overlap checks against co-moving strands.
- `listCrossovers` and `getValidCrossoverPositions` return strings, not dicts. To use their output programmatically, parse with regex + `ast.literal_eval`.
- tacoxDNA's initial nucleotide placement depends ONLY on helix lattice positions (row, col), NOT on crossover connectivity. A design with all crossovers and one with zero crossovers produce identical 3D coordinates. The geometric reward (flatness, planarity, circularity) catches wrong helix arrangements (flat sheet vs grid: 0.95 vs 0.42) but cannot detect missing crossovers. To get crossover-sensitive 3D feedback, you would need oxDNA molecular dynamics relaxation (too slow for training). Use geometric reward + structural verifier together.
- Staple double crossovers have widely spaced half-crossover positions (e.g., low_idx=63, high_idx=83) unlike scaffold crossovers which are adjacent (88, 89). `moveCrossover` doesn't yet handle staple crossovers correctly — the intermediate strand segments between the two half-crossover positions aren't accounted for.
- Headless screenshot capture works: `scene.render(painter, source=items_rect)` on a `QImage` with `QT_QPA_PLATFORM=offscreen`. Use `items_rect = scene.itemsBoundingRect()` with margins for good framing.
- `from cadnano2.views.agent.agentmethods import AgentMethods` must be done AFTER `cadnano.initAppWithGui()` — importing AgentMethods triggers Qt font initialization which crashes if no QApplication exists. Always: `os.environ['QT_QPA_PLATFORM'] = 'offscreen'` → `initAppWithGui()` → `import AgentMethods`.
- tacoxDNA (`cadnano_oxDNA.py`) outputs files named `<input>.oxdna` and `<input>.top` (appends extension to the full input filename including `.json`). 1 oxDNA length unit = 0.8518 nm. tacoxDNA needs `he` (hexagonal) for honeycomb lattice designs.
- For PCA-based shape analysis of oxDNA coordinates: PC1=length, PC2=width, PC3=thickness. Flatness ratio = thickness/length. A 6-helix x 126bp flat sheet gives ~0.058 flatness and ~0.63 nm planarity RMS (about 1 DNA diameter thick).
- `deleteExposedFragments` (OR condition: either end free) is too aggressive after placing non-loop crossover patterns — it removes strands that are part of the routing but have one exposed end. Use `deleteOrphanFragments` (AND condition: both ends free) to only remove edge stubs outside the crossover range.
- Different honeycomb neighbor directions (p0, p1, p2) have different valid crossover position offsets. In a 4-helix linear chain, H0-H1 (p0) has edges at low_idx 1/116, while H2-H3 (p2) has edges at 4/120. The PI's observation "not necessarily in the same positions" is because each pair uses a different direction's crossover tables.
- Scaffold crossover edge detection: marking both first AND last valid positions as "edges" for half-crossovers is wrong. Each helix pair needs at most ONE half-crossover (the routing turn), determined by helix parity: even parity exits at the HIGH (rightmost) position, odd exits at LOW (leftmost). The routing turn must be force-included in recommended positions because the spacing filter (21bp) can exclude it when it's close to the last interior position.
- When creating multiple cadnano designs in the same process, call `dc.newDocument()` between designs to reset the document. Without this, `_make_methods(app)` gets the same `documentControllers` and helices persist from previous designs.
- Cross-section circularity distinguishes shape classes: flat sheet ~0.48, tube ~0.55, 2×3 grid ~0.84 (near-square cross-section). Higher circularity = more compact cross-section.
- Half crossover handedness (left vs right): A full double crossover consists of a LEFT half (at the Low index) and a RIGHT half (at the High index). `honeycombScafLow` positions are Left half crossover positions, `honeycombScafHigh` positions are Right half crossover positions. At the LEFT side of the structure (scaffold turn), use a RIGHT half crossover (High index position). At the RIGHT side, use a LEFT half crossover (Low index position). **Use `createHalfCrossover` directly at the correct table position** — the double-then-remove approach (create double, remove one half) does NOT produce correct visual results. `createHalfCrossover` handles strand ordering automatically via `_isHighCrossoverPosition`: Low positions use even→odd (even is 5p), High positions use odd→even (odd is 5p).
- **Serpentine scaffold routing cannot use `createXover`**: `part.createXover()` splits strands at the crossover position, and subsequent crossovers can split already-connected strands, breaking the path. For serpentine (one-crossover-per-pair) routing, create correctly-sized strands between crossover positions and connect them directly using `strand5p.setConnection3p(strand3p)` + `strand3p.setConnection5p(strand5p)` + oligo merging. This bypasses the split mechanism entirely and produces a single continuous scaffold oligo.
- **Rectangular origami scaffold uses ~91% of helix length**: In honeycomb lattice, crossover positions at helix edges are at offset 1-4 (not 0), so the scaffold doesn't reach the very ends. For m13mp18 (7249 nt) on 24 × 294bp helices, the routed scaffold is ~6762 bp — the remaining 487 nt are consumed by single-base insertions (also serves as twist correction).
- **autoBreak `from . import staplegraph` fails** when called from scripts outside the package. Fix: use `importlib.util.spec_from_file_location` to pre-load `staplegraph.py` into `sys.modules['cadnano2.plugins.autobreak.staplegraph']` before importing `autobreak.py`.
- **Honeycomb grid default size is 30 rows × 32 columns**: Helix positions must stay within (0-29, 0-31). A 24-helix row starting at column 20 reaches column 43 (crash). Start at column 4 instead: 4+23=27 < 32.
- **oxDNA input files need `time_scale = linear`, `refresh_vel = true`, and `trajectory_file`**: These mandatory keys are not obvious from examples. Without them, oxDNA fails with cryptic error messages.
- **oxDNA from source requires CMake < 4.x fix**: The `CMP0037` policy must be set to NEW (not OLD) in `CMakeLists.txt`. CUDA build fails with modern cmake/nvcc; CPU-only build works. Use `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`.
- L-shaped honeycomb designs (3 horizontal + 2 vertical helices) produce a thicker cross-section (4.6 nm vs 2.4 nm flat sheet) and higher planarity RMS (1.28 nm) due to the out-of-plane bend at the junction. The PCA-based analysis captures this as increased flatness ratio (0.11 vs 0.058).
- **Honeycomb lattice cavity routing requires ≥4 rows.** On honeycomb, cross-row connections (p1 direction) exist only at alternating columns (odd columns for even start_row). A 2-row grid cannot route a scaffold around a cavity because boundary helices become degree-1 dead ends. Minimum 4 rows needed. Parity constraints: N_ROWS even, N_COLS odd, start_row%2 ≠ start_col%2. This ensures all corners have cross-row connections. The Hamiltonian cycle finder (DFS + backtracking) works in <1ms for grids up to ~42 nodes.
- **Honeycomb layer counting: 2 grid rows = 1 honeycomb row = "2-layer".** PI confirmed definitively: 2 grid rows = 1 honeycomb row = what they call a "2-layer rectangle" = "2xN" in their notation. NxM = grid rows × columns. Do NOT overthink this — 2 grid rows IS 2-layer. The staggered even/odd parity positions within one grid row are sub-structure, not separate layers.
- **Standard DNA origami uses DENSE scaffold crossovers, not serpentine.** PI's `2x12_rectangle_cavity.json` template has multiple double crossovers per helix pair (4+ crossovers per pair). The scaffold weaves back and forth between adjacent helices. This is the standard cadnano pattern — each helix pair shares 2-3 double crossovers, creating 3-4 segments per helix within each pair. My serpentine approach (1 crossover per pair) was fundamentally wrong for DNA origami. Use `part.createXover()` at ALL valid honeycomb positions between neighbors, not just one turn position. The dense pattern naturally handles the cavity: left and right segments of split helices are visited through the zigzag weave.
- **Cavity helix gaps must stay EMPTY — do NOT fill them.** When shifting scaffold data to extend a design, the gap between left and right segments of cavity helices is the actual cavity. My gap-fill logic incorrectly added continuous scaffold through the cavity region (positions 75-337 on H16-H19). The PI had to manually clear these. Only fill gaps on NON-CAVITY helices.
- **Crossover positions must be ALIGNED — same index on both helices.** When shifting crossovers, both sides must land at the same bp index. My shift logic moved positions independently per helix, causing skew (e.g., H16[337] vs H17[338]). Always verify: for every crossover `H_a[idx] → H_b[idx']`, check `idx == idx'`. The PI corrected H16/H18 crossovers from 337→338 to align with H17/H19 at 338.
- **Step 2 already moved cavity right-side half-crossovers** — the shift at CUT=170 moved H16-H17 and H18-H19 crossovers from their original positions to 338. This was supposed to be Step 4 (expand cavity). Track which crossovers have already been moved to avoid double-moving.
- **oxDNA relaxation: `max_backbone_force_far` is critical**. The old pipeline used 10.0 for MD relaxation — far too permissive, letting the structure blow apart. The PACE bricks_crystal recipe uses a staged approach: 0.1 (gentle relax) → 1.0 (production relax). The gentle stage lets the structure settle without the backbone flying apart, then the production stage allows more realistic forces. Also: John thermostat (Langevin, `diff_coeff=2.5`, `newtonian_steps=103`) is proven stable for DNA origami on PACE; Bussi thermostat with tau=1000 was not tested on production structures. Use `dt=0.003` (not 0.002), `verlet_skin=0.5` (not 0.15) for MD, and `salt=1.0` for minimization.

## JSON-Level Scaffold Manipulation (2026-03-19)

- **Never use crossover references to determine scaffold direction after shifting.** When step2_extend shifts data rightward, position 169's 3' reference changes from 170 to 296 (the shifted target). Using this reference to determine fill direction gives WRONG direction for even helices. Always use helix parity: even (num%2==0) → right, odd → left.
- **Creating a crossover at an EMPTY position silently fails.** `move_cavity_boundary` tried to place a crossover at the new gap boundary, but the position was EMPTY (inside the original cavity gap). The `if sa[pos] != EMPTY` check silently skipped it. Fix: create a scaffold entry at the position first, then place the crossover.
- **The last pair (H22-H23) must NOT have a midseam crossover.** This pair connects the two scaffold halves via edge-only crossovers. step3_move_midseam was iterating all non-cavity row13 pairs, including H22-H23. It tried to remove a non-existent old seam (no-op) but ADDED a new one, splitting the scaffold into 2 oligos.
- **R13 cavity helices (H16-H19) have their right segment at exactly CUT=170.** step2_extend must NOT fill the extension gap for these helices — the fill creates positions (170..170+shift) that become interior to the expanded cavity gap when step4 moves the boundary beyond 170. Let step4 handle the R13 extension fill.
- **Centering the cavity requires moving BOTH boundary crossovers.** The original 4-step process only moved the right boundary while keeping the left fixed at template position 67/74. Both left and right boundary half-crossovers must be moved symmetrically from the helix center.
- **cadnano's `decode` (legacydecoder.py) hangs on designs with odd segment counts.** The `isSegmentStartOrEnd` function in legacydecoder detects strand boundaries. If the count is odd, the assertion `assert(len(segs) % 2 == 0)` fails, but a typo (`AssertionError` instead of `AssertionError`) means it's never caught. The loop trying to process segments goes out of bounds or hangs.
- **PACE shared oxDNA binary removed during RHEL9 migration.** The path `/storage/coda1/p-yke8/0/shared/oxDNA/build/bin/oxDNA` no longer exists. Use the user-built binary at `~/scratch/oxDNA/build/bin/oxDNA` (built with CUDA 12.1.1, gcc 12.3.0). Load modules: `module load cuda/12.1.1 gcc/12.3.0`.
- **autobreak `staplegraph` import fails from scripts.** The `__init__.py` in `cadnano2/plugins/autobreak/` has `import cadnano, util` (old module names). Use `importlib.util.spec_from_file_location` to load `staplegraph.py` first, then `autobreak.py`, bypassing the broken `__init__.py`. Set up the package module in `sys.modules` so the relative import `from . import staplegraph` succeeds.
- **NumPy 2.0 removed `ndarray.ptp()`.** Use `np.ptp(arr, axis=0)` or `np.max(arr, axis=0) - np.min(arr, axis=0)` instead of `arr.ptp(axis=0)`.
- **To expand cavity within 2×12 template, use ORIG cavity set in steps 2-3.** When converting non-cavity pairs (H2-H3, H8-H9) into cavity pairs, treat them as non-cavity in steps 2 (extend) and 3 (move midseam). This fills the extension gap and moves their midseam to center. Then step 4 converts them to cavity by placing boundary crossovers and clearing the gap. Using the full cavity set in steps 2-3 skips gap-fill and midseam moves, leaving the pairs in an inconsistent state.
- **step4 move_boundary right-side "expand gap" can destroy the left boundary.** When the old right boundary position (e.g., 163) is to the LEFT of the new left boundary (173), the right-side gap expansion clears positions 163-224, destroying the left boundary crossover at 173. Fix: don't clear during right boundary expansion; let the post-step gap-clearing handle it.
- **Find right boundary BEFORE moving left boundary.** After placing the left boundary crossover, searching for the right boundary may find the left boundary crossover instead (if the old right boundary was at a lower position). Search for all intra-pair crossovers before moving anything, then use the correct one.
- **Helix parity is (row+col)%2, NOT num%2.** In the original 2×12 template, num%2 happens to match (row+col)%2 because helices are numbered sequentially along columns. But when adding new helices with higher numbers, num%2 diverges from physical parity. H24 at (12,21) has num%2=0 (even) but (12+21)%2=1 (odd). ALL parity-dependent logic (scaffold direction, fix_scaffold_directions, cadnano_verifier) must use (row+col)%2 from the vstrand's row/col fields, not num%2. This is Failure #9.
- **Template extension pattern: clone same-parity, wire inter-pair, move last pair.** To add columns: (1) create new helices at adjacent columns, (2) clone scaffold data from same-parity helix in the same row, (3) add inter-pair crossovers using existing inter-pair positions as template, (4) add midseam to old last pair, (5) new outermost R13 pair becomes the last pair with edges only.
- **Clone function must use EXPLICIT partner, not auto-detect.** The auto-detect picks the helix with MOST crossovers as "partner." For the last pair (H22-H23), H22 has 4 crossovers to H21 (inter-pair) but only 2 to H23 (intra-pair edges). Auto-detect picks H21 as partner instead of H23. Always specify the pair partner explicitly.
- **Clone must remove ALL non-self, non-partner helix refs.** The clone function originally preserved inter-pair crossover refs (e.g., H1's refs to H2 at positions 64/65/200/201). These stale refs in the clone create one-directional crossovers that fragment the scaffold. Replace all non-self/non-partner refs with same-helix entries.
- **Adding inter-pair crossovers splits the target helix into extra segments.** Template H0 is one continuous segment (only intra-pair crossovers at edges). Adding inter-pair crossovers at H0[64/65/200/201] creates 5 segments. The scaffold path enters H0 only twice (via H1 at 5/246), leaving middle segments unreachable. Template extension requires restructuring the scaffold path, not just adding crossovers.
- **Inter-pair crossovers go on the INNER helix of the new pair, NOT on H0.** When extending the template with new columns, H0 (the outermost helix) keeps its original structure unchanged. The new pair's inner helix (H25, adjacent to H0) gets the inter-pair crossovers connecting to H0. H0 is one continuous segment with only intra-pair crossovers — adding inter-pair crossovers to it splits it into unreachable segments. The OUTER helix of the new pair (H24) only has intra-pair crossovers, just like H0 in the original template.
- **Use `part.renumber(coordList)` after extending templates.** Cadnano2 has a built-in renumber function that assigns even numbers (0,2,4...) to even-parity helices and odd (1,3,5...) to odd-parity, based on the coordList ordering. This ensures num%2 == (row+col)%2 and gives intuitive sequential numbering.
- **Scaffold routing order for 2×14: new_R12_pair → existing pairs → new_R13_pair.** The chain is: H24↔H25 → H25↔H0 → H0↔H1 → ... → H22↔H23 → H23↔H26 → H26↔H27. New R13 pair (H26-H27) is the last pair with edges only.

## Template Extension & Renumbering (2026-03-25)

- **Inter-pair crossover direction: LOW position = crossover IN (5' from partner), HIGH position = crossover OUT (3' to partner).** At a double crossover between H_a and H_b at positions [low, high]: H_a[low] has 5' FROM H_b (entry), H_a[high] has 3' TO H_b (exit). Inverting this creates mini-loops instead of zigzag traversal. This is Failure #10.
- **Manual JSON renumbering is essential when adding columns.** When extending a template with new helices, the helix numbers won't match the routing order. Renumber by: (1) define the desired routing order (row 12 from highest col to lowest, row 13 from lowest to highest), (2) change every `num` key in each vstrand, (3) update every helix reference in ALL `scaf` and `stap` tuples to use the new numbers. This ensures sequential H0→H1→...→H_N numbering that matches the scaffold routing path. Always renumber AFTER all crossover wiring is complete.
- **Shape design = strand trimming, NOT lattice placement.** When asked to make a shape (cross, arrow, diamond), the helices stay on a flat 2-layer grid. The shape comes from moving edge crossovers to control strand lengths — short strands for arms, full-length for the bar. `strand.resize()` automatically moves edge half-crossovers to new endpoints. The earlier lattice-based crosses (placing helices in a cross pattern) were the wrong approach. PI correction: "design the pattern in the strands, which is done by selectively moving edge crossovers."
